# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

CASP (Controle de Assessoria e Prestação de Serviços Contábeis) — a system for an accounting firm that manages public-budget/fiscal bookkeeping (orçamento, execução orçamentária, LOA) on behalf of multiple Brazilian municipalities (prefeituras/câmaras) as clients. Backend: Django + DRF. Frontend: React 19 + Vite + MUI.

`DADOS/` at the repo root holds raw source documents for one client (PDFs/ODS from the "ASPEC" accounting system) — it is not committed and is the input for the import pipeline described below.

## Architecture

### Multi-tenant access scope (Município → {UG, Órgão} → Unidade Orçamentária)

This is the core domain model and governs every query in the app, because one accounting-firm login must only see the municipalities/entities it's been granted. **It is not a strict tree** — `Orgao` and `UnidadeGestora` are siblings under `Municipio`, not nested:

- `apps.municipios`: `Municipio` has two separate child collections — `UnidadeGestora` (prefeitura, câmara, and critically also every "Fundo Municipal de X"/FUNDEB, each a legally distinct budget-executing entity) and `Orgao` (the organizational chart: secretarias/gabinetes, independent of which UG executes them). `UnidadeOrcamentaria` is the join point: it belongs to one `Orgao` *and* one `UnidadeGestora`. **A single órgão routinely has unidades orçamentárias under different UGs** — e.g. "Secretaria Municipal de Educação" has one unidade under "Fundo Municipal de Educação" and another under the FUNDEB UG — discovered by cross-referencing the real org chart (`ESTRUTURA.pdf`) against what had been (wrongly) assumed; see `importar_estrutura_organizacional` below. Never assume `Orgao` implies one `UnidadeGestora`.
- `apps.usuarios.Usuario`: custom user model, **login by CPF** (`USERNAME_FIELD = "cpf"`), not email/username.
- `Usuario.is_equipe_escritorio`: office-staff users see everything, unrestricted. Client users (municipality/câmara staff) do not and must be granted `VinculoAcesso` records.
- `VinculoAcesso`: `unidade_gestora` and `orgao` are independent optional fields (not nested) — município-wide if both blank, UG-wide if only `unidade_gestora` set, whole-órgão-across-every-UG-it-has if only `orgao` set, or restricted to that órgão's units within that specific UG if both are set. Also carries a `papel` (ADMIN/GESTOR/ANALISTA/VISUALIZACAO) that is currently stored but not yet enforced anywhere.
- `apps.usuarios.permissions` / `apps.municipios.permissions` (re-exported) provide the helpers every viewset's `get_queryset()` must use to scope results: `municipios_acessiveis`, `unidades_gestoras_acessiveis`, `orgaos_acessiveis` (a UG-level vínculo reaches an órgão if *any* of its unidades orçamentárias is in that UG, via `Q(unidades_orcamentarias__unidade_gestora_id__in=...)`), `tem_acesso`, `aplicar_filtro_ativo` (hides `ativo=False` rows by default, `?incluir_inativos=1` to see them — added 2026-11-11, see below), and two permission classes: `IsEquipeEscritorioOuSomenteLeitura` (read is scope-filtered for everyone; write requires `is_equipe_escritorio` or superuser) and `IsEquipeEscritorio` (no access at all for client users, not even read — used only by `Usuario`/`VinculoAcesso`, since a prefeitura/câmara user must never see other users' names/CPFs). **Any new viewset exposing scoped data must filter its queryset through one of these helpers** — there is no row-level DB filtering, it's all application-level.
- Frontend mirrors this: `ScopeContext` loads the municipalities visible to the logged-in user and holds the currently selected `municipioSelecionadoId`; pages read/write against that selection.
- `Usuario`/`VinculoAcesso` now have real CRUD (`UsuarioViewSet`/`VinculoAcessoViewSet`, `apps/usuarios/views.py`, both `IsEquipeEscritorio`) and a frontend page (`UsuariosPage.tsx`) — previously only manageable via Django admin. `UsuarioSerializer.password` is `write_only`, never round-tripped; `create`/`update` call `set_password()`/`set_unusable_password()` explicitly, never a plain `ModelSerializer` save of the raw value. Vínculos are managed from inside `UsuariosPage.tsx` (a "Gerenciar" button per user opens a dialog hosting a second, nested `CrudManager` scoped by `parametrosExtras={{usuario: <id>}}`) rather than a standalone page, since a vínculo only makes sense in the context of one user.

### CRUD completo + auditoria + agregados (2026-11-11)

Full audit (CRUD coverage, frontend coverage, indexes, timestamps, report query patterns) found: 20/34 models had full CRUD, 11 were read-only (every imported "fato"), and 3 had **no API at all** (`Usuario`, `VinculoAcesso`, `Importacao`). User asked for CRUD everywhere + "sophisticated" modeling for future reports; confirmed via plan mode: (1) give fatos full CRUD but track origin/who-edited, (2) `Importacao` gets CRUD/history only, no upload→parser dispatcher yet, (3) backend aggregate endpoints, not materialized tables.

### Orçamento domain (`apps.orcamento`)

Models the full Brazilian municipal-budget classification hierarchy per exercício (fiscal year): `Exercicio` → `LOA` (one per exercício) → `Programa`/`Acao` (LOA-specific) crossed with national/STN catalogs (`Funcao`, `Subfuncao`, `CategoriaEconomica`, `GrupoNaturezaDespesa`, `ModalidadeAplicacao`, `ElementoDespesa`, `Subelemento`, and `FonteRecursos` — **no longer UG-specific, see fix below**). A `RubricaOrcamentaria` is the full combination of all of the above (órgão + unidade orçamentária + classificação funcional/programática + classificação econômica + fonte) for one LOA — it's the unique key that `LancamentoExecucaoOrcamentaria` (one row per rubrica per `mes_referencia`) reports monthly execution against (`empenhado`/`liquidado`/`pago`, both monthly and accumulated, plus dotação inicial/atualizada).

**`FonteRecursos` was wrongly UG-scoped — fixed 2026-11-12.** User report: "as fontes de recursos estão duplicadas por UG, ela é única para todas as UGs", backed by two new consolidated validation PDFs they generated from ASPEC (`DADOS/VALIDAÇÕES/DESPESA_FONTE.PDF`, `RECEITA_FONTE.PDF` — "Demonstrativo das Despesas/Receita por Fonte", Jan-Out/2026, grouped by fonte código alone, no UG dimension at all). Investigated before touching anything: `FonteRecursos` had `unidade_gestora` as part of its unique key (`unique_together(unidade_gestora, codigo)`), so the same real-world fonte got a separate row per UG — confirmed with the data itself: 138 rows but only 89 distinct códigos, and **zero** cases where the same código had a different nome across its duplicate rows (airtight evidence it's the same logical fonte, not coincidentally-matching names). This was also the only classification catalog in the whole app scoped this way — `CategoriaEconomica`/`GrupoNaturezaDespesa`/`ModalidadeAplicacao`/`ElementoDespesa`/`Subelemento` are all global by código already (`ClassificacaoOficialMixin`'s own docstring says "catálogos nacionais, compartilhados por todo município — nunca filtrados por município"), and `importar_fontes_recursos()`'s own docstring already said "o catálogo Fontes de recursos do ASPEC não varia por UG" — the bug was the model contradicting its own documented intent, not an ambiguous design choice.
- **Fix**: removed `unidade_gestora` from `FonteRecursos` entirely; `codigo` is now the sole (globally) unique key, matching its sibling catalogs. Migration `orcamento/0012_mesclar_fontes_recursos_duplicadas.py` (data, `RunPython`, irreversible) runs **before** the schema migration (`0013_...`): for each duplicated código, picks a canonical row and repoints every FK from the 5 tables that reference `FonteRecursos` (`RubricaOrcamentaria`, `fiscal.RubricaReceita`, `financeiro.SaldoBalancoContaFonte`/`SaldoContaBancariaFonte`/`RestoAPagar`) from the duplicate rows onto the canonical one before deleting the duplicates — necessary both because `codigo` can't become `unique=True` while duplicates exist, and because all 5 FKs are `on_delete=PROTECT` (deleting a still-referenced duplicate would fail outright). Verified zero data loss before/after: row counts and value sums on all 5 referencing tables matched exactly (e.g. `RubricaOrcamentaria` 1491 rows / R$250.000.000,00 dotação inicial, `RestoAPagar` 4110 rows / R$27.766.684,50 inscrição processada — identical before and after the merge). `services.py`'s ~10 `FonteRecursos.objects.get_or_create(unidade_gestora=..., codigo=...)` call sites across every import service (despesa and receita dotação, saldo de balanço, saldo de conta bancária, restos a pagar) dropped the `unidade_gestora` kwarg; `_resolver_fonte_por_nome()` (receita side, matches by nome since that source never gives a código) lost its "existe nesta UG? existe em outra UG, empresta o código?" 3-step logic entirely — now just "existe pelo nome? senão cria com código sintético", 2 steps, no UG concept left at all.
- **Frontend**: `/fontes-recursos/` no longer accepts/needs a `?unidade_gestora=` filter (`FonteRecursosViewSet.get_queryset` is now a plain `.objects.all()`, matching `ElementoDespesaViewSet`'s pattern). `FontesRecursosPage.tsx` (cadastro) dropped the Unidade Gestora column/field entirely. `RestosAPagarPage.tsx`'s creation dialog had a dependent UG→Fonte select pair (`carregarFontesDaUG()`, fonte select disabled until a UG was picked) — replaced with a single always-enabled global fonte list loaded once on mount, same pattern as the UG list beside it.
- **Validated against both new PDFs before considering this done**, not just by inspecting row counts: receita side matches **exactly**, all 40 fontes and the R$230.811.437,73 grand total, to the cent, grouping `LancamentoExecucaoReceita` by `fonte_recursos__codigo`. Despesa side matches on every fonte except one (`15000000`): PDF R$51.529.364,73 empenhado vs. our R$51.551.004,95 (R$21.640,22 off, ~0,04%, same-direction and roughly double the liquidado/pago gap on that one line) — checked for the obvious causes (duplicate empenho numbers within that fonte: none found) and left as a small, isolated, pre-existing residual unrelated to the duplication bug being fixed here, not something to chase further without more signal from the user.
- **`FonteRecursos.natureza`/`natureza_label` added, 2026-11-12** — user report: "todas as fontes que começam com 1. é do exercício e todas as fontes que começam com 2. é superávit... não deveria haver receita na fonte 25401070". Added `NaturezaFonteRecursos` (`DO_EXERCICIO`/`SUPERAVIT_FINANCEIRO`) as two `@property`s on `FonteRecursos` (`natureza`/`natureza_label`), derived purely from `codigo[:1]` ("1"→exercício, "2"→superávit, anything else incl. the synthetic `"RECxxxxx"` codes→`None`) — confirmed via shell: 47 fontes="1", 40="2", 2 `None`. No migration needed (pure computed properties, `makemigrations --check --dry-run` clean). Exposed via `FonteRecursosSerializer` (explicit `CharField(read_only=True, allow_null=True)` declarations, same pattern as every other `@property`-on-serializer in this app) and shown as a read-only "Natureza" column on `FontesRecursosPage.tsx` — this is what surfaced `CrudManager.tsx`'s `somenteColuna: boolean` flag on `CampoFormulario` as declared-but-never-implemented dead code (it rendered in the table but was never filtered out of the edit/create dialog); fixed by changing the dialog's field list from `campos.map(...)` to `campos.filter((c) => !c.somenteColuna).map(...)` — the table rendering was already correct and untouched. Verified in browser: column shows correctly, edit dialog correctly omits it.
- **The actual 25401070 anomaly was a frontend bug, not a data bug — found and fixed 2026-11-12** — `LancamentoExecucaoReceita`/`RubricaReceita` have zero rows for fonte 25401070 directly; the "receita leaking into it" the user saw on `RelatorioFinanceiroPage.tsx`'s Relatório de Disponibilidade por Fontes was `montarDisponibilidades()`'s `grupo()` helper keying its `Map<string, GrupoDisponibilidade>` by fonte **nome** instead of **código**. This was correct *before* the UG-duplication fix above (código varied per UG, nome was the only stable cross-UG key) but became actively wrong afterward: 15401070 ("Recursos do Exercício") and 25401070 ("Superávit Financeiro") share the identical descriptive name "Transferências do FUNDEB - Impostos 70%", so the name-keyed `Map` silently merged 25401070's real (near-zero) despesa row with 15401070's large receita row into one display line. Fixed by switching the `Map` key to `codigo`. Verified in browser: the two fontes now render as separate rows — 15401070 keeps its real R$33.190.548,51 receita, 25401070 shows R$0,00 receita and only its own tiny R$0,01 despesa — confirming the user's claim ("não deveria haver receita na fonte 25401070") is now true in the system.

`RubricaOrcamentaria.origem_dotacao` (`OrigemDotacao`: `ORCAMENTO` / `CREDITO_SUPLEMENTAR` / `CREDITO_ESPECIAL` / `CREDITO_ADICIONAL`) is a provenance flag, correctable over time (the most specific source wins), never a ledger. `ORCAMENTO`/`CREDITO_SUPLEMENTAR`/`CREDITO_ESPECIAL` come from `importar_fichas_despesa()` (ASPEC natively classifies every combination this way, even ones with no value yet); `importar_dotacoes_loa()` only ever sets `ORCAMENTO` (its source PDF doesn't distinguish credit types) and should be treated as provisional until `importar_fichas_despesa` runs. `CREDITO_ADICIONAL` is the fallback `importar_empenhos()` uses only when an empenho references a classification neither the LOA nor the fichas catalog ever anticipated. This is the mechanism that replaced the monthly PDF balancete as the source of dotação data (see Import pipeline below).

`Empenho` is the empenho-level detail behind those monthly aggregates (número do empenho, data de abertura, credor, histórico), FK'd to `UnidadeGestora` + `RubricaOrcamentaria`, natural key `(unidade_gestora, numero)`. Its `valor_empenho`/`valor_liquidado`/`valor_pago` are **denormalized totals, never written directly** — they're recomputed (`Empenho.recalcular_totais()`) as the sum of the empenho's `EmpenhoMovimento` children. This split exists because the ASPEC empenhos report is exported **one spreadsheet per month**, and when an empenho from an earlier month still has activity, it reappears in a later month's file showing only *that month's* movement (`valor_empenho` usually 0 — no new commitment — with whatever liquidou/pagou that month), not a repeated running total. Treating a later file's row as a corrected snapshot (overwrite, or even `max()`) silently destroys previously-known totals — this happened once already during development; the per-month-row + sum design makes the import order-independent and safe to re-run instead. `EmpenhoMovimento`'s natural key is `(empenho, mes_referencia)`, and **`mes_referencia` must come from the report/file's own header** ("Mês de `<Nome>`/`<ano>`", parsed in `aspec_empenhos.py`), never from the row's `Data Empenho` — that date is the empenho's fixed origin date and doesn't change across the files it reappears in, so keying by it instead of the file's month collapses different months' movements onto the same row (the other bug hit during development, before this design existed).

### Receita domain (`apps.fiscal`)

Mirrors the despesa domain's dotação/execução split, but structurally simpler because receita has no organizational dimension (órgão/unidade orçamentária/função/subfunção/programa/ação don't apply — a receita belongs to the município as a whole) and no multi-stage lifecycle (despesa has empenho→liquidação→pagamento; receita is regime de caixa, so a collection event is final the moment it's recorded):

- `RubricaReceita` is the dotação (previsto) side — classificação da receita × fonte de recursos × Unidade Gestora arrecadadora, one row per LOA, each combination carrying its own `valor_orcado` (confirmed by summing every row in a sample LOA: matches the source PDF's own grand total to the cent — fonte-level lines are independent budgeted amounts, not a sub-breakdown of a bigger per-código total, exactly like despesa's `RubricaOrcamentaria` × fonte). Reuses `apps.orcamento.FonteRecursos` — it's the same vinculação catalog despesa already uses (confirmed by name: every fonte named in the receita LOA PDF already exists, under that same name, somewhere on the despesa side).
- Only two Unidade Gestora siglas ever appear on the receita LOA side: `PMNP` (Prefeitura) and `CMNP` (Câmara) — unlike despesa's 8 UGs/fundos, the fundos don't arrecadar directly, they receive repasses from the Prefeitura (visible in the execução data as negative "991.x"-coded dedução/complementação-FUNDEB entries, which are legitimate classification codes in their own right, not anomalies).
- `LancamentoExecucaoReceita` is the receita-execução source — one row per rubrica (código × fonte) per mês. Source: "Demonstrativo da receita por classificação econômica" (`R01.PDF`..`R09.PDF`, one file per month, each covering only that month — unlike the old despesa balancete PDF, not cumulative). This is the only receita source with fonte de recursos per lançamento. FK's to `RubricaReceita` (creating new rows at `valor_orcado=0` for combinations the LOA didn't anticipate, same `CREDITO_ADICIONAL`-style fallback as despesa) and resolves `FonteRecursos` by the real código this report provides (more reliable than `importar_fichas_receitas`'s name-based fallback, since this source isn't missing the código). Always attributed to Unidade Gestora "01" (Prefeitura) — the report doesn't distinguish UG, and Câmara's receita-side rubricas are 100% `valor_orcado=0`, so there's no real revenue to misattribute.
- **`Arrecadacao` (transaction-level receita from `RECEITAS.ods`, superseded by `LancamentoExecucaoReceita` on 2026-11-10) was removed entirely on 2026-11-12** — model, migration (`fiscal/migrations/0008_...`, drops the table), parser (`aspec_receitas.py`), service (`importar_receitas`), management command, dispatcher mapping (`TipoRelatorio.RECEITAS_ARRECADACAO`), API route (`/arrecadacoes/`), and frontend type/upload-option all deleted together, confirmed via explicit user decision (not left dormant, as originally deferred below). It had run ~0.3% below `LancamentoExecucaoReceita`'s net total every month (same sign each time, confirmed not a parsing bug) — the two were always independent measurements, never reconciled, so losing the cross-check is a known, accepted tradeoff of the removal.

### Financeiro domain (`apps.financeiro`)

Three report types, all reusing `orcamento.FonteRecursos` (resolved by código, which every source here always gives). **UG and período are always read from the report's own header text, never from the filename or folder name** — this was an explicit requirement before building the first two pipelines, given the established history of filename/folder names lying about scope (the despesa "BR0x consolidado" trap, the empenho "mês vem da Data Empenho" trap). Every parser raises (aborts the import) if a header's UG name doesn't match any `UnidadeGestora` for the município, rather than guessing or defaulting — `resolver_unidade_gestora_por_nome()` in `services.py` does this accent/case-insensitively (the despesa "Câmara"/"Camara" mismatch recurs here too, on `BAL_CMNP.PDF`).

- `SaldoBalancoConta`/`SaldoBalancoContaFonte` — from "MOVIMENTOS DE SALDOS DE BALANÇO". A **snapshot at one date**, not a monthly series — the only data seen so far is `02/01/2026` (the exercício's opening balance). Each conta belongs to a `categoria` ("Banco" / "Depósitos de diversas origens" / "Consignações" — not every UG has all three). The report's own trailing summaries ("DETALHAMENTO da conta `<categoria>` por Fontes de Recursos" mid-file, "TOTAL das contas por Fontes de Recursos" at the end) repeat data already read — skipped rather than double-counted; validated by summing `SaldoBalancoContaFonte` by (código, natureza) for the UG with the most accounts (Prefeitura) and matching that footer exactly, to the cent.
- `SaldoContaBancaria`/`SaldoContaBancariaFonte` — from "Relação de saldos - Por UG titular da conta". The date printed in the header is the **last day of the month** ("31/01/2026" for mês 01). The same folder has a `CONSOLIDADOxx.PDF` that is a genuinely **different report** ("Saldo das fichas do sistema financeiro", columns "SALDO DEVEDOR"/"SALDO CREDOR") — not a sum of the per-UG files at all, and not used here. This report has three nested layers of trailing summary to skip ("TOTAL DA CONTA BANCO...", "Detalhamento da conta BANCO por fontes de recursos" + its own "TOTAL detalhamento...", and a final "Detalhamento geral de todas as contas" + "TOTAL GERAL DETALHAMENTO TODAS CONTAS") — missing the first two and only catching the last one was a real bug caught during development (it silently doubled every fonte total, since the mid-file resummary lines parse identically to real fonte lines); fixed by treating all four trailing-summary prefixes as stop-parsing markers.
- **Fonte mudou de "um PDF por UG" para "um PDF cobrindo todas as UGs", 2026-11-12** — o ASPEC passou a exportar `SaldoBalancoConta` (antes `BAL_<SIGLA>.PDF`, 8 arquivos) e `SaldoContaBancaria` (antes `DADOS/SALDO/CONTAS/<mês>/<SIGLA><mês>.PDF`, 8 arquivos por mês) como um único PDF cada (`SALDO_BALANCO.PDF`; `CONTAS<mês>.PDF`) — mesma estrutura que `RestoAPagar` já tinha (nome da UG repetido na 3ª linha de cada página, mudando quando a seção de UG muda). Reportado pelo usuário como bug ("RP de outubro só importou a prefeitura" — na verdade era `SaldoContaBancaria`, não restos a pagar, que já suportava múltiplas UGs por arquivo sem mudança nenhuma). Dois parsers tiveram que ser reescritos para ler a UG por página em vez de uma vez só para o arquivo inteiro (`aspec_saldo_balanco.py`, `aspec_saldo_conta_bancaria.py`) — e, mais sutil, **os dois tinham um estado de "pulando resumo do fim" que nunca era resetado**, porque no formato antigo nada real vinha depois do resumo de uma UG (era literalmente o fim do arquivo); agora a próxima UG começa logo em seguida, então ambos os parsers resetam esse estado quando a UG realmente muda de nome, não só ao ver um marcador específico de fim-de-resumo (nenhum aparece de forma confiável). `aspec_saldo_conta_bancaria.py` também tinha um `parando=True; break` que abortava o arquivo INTEIRO ao ver o primeiro resumo — exatamente a causa do "só importou a prefeitura", já que a Prefeitura é a primeira UG do arquivo. `services.importar_saldo_balanco()`/`importar_saldo_conta_bancaria()` passaram de "resolve uma UG, grava" para "agrupa as linhas por UG (cada uma já carrega seu próprio `unidade_gestora_nome`), resolve e grava cada grupo independentemente" — reimportar continua substituindo só a UG+data/mês daquele grupo, UGs ausentes do arquivo não são tocadas. Validado reimportando CONTAS01-10 e SALDO_BALANCO: os totais batem exatamente com os já existentes no banco (131 contas/8 UGs em janeiro, 136 contas/183 fontes no saldo de balanço — ambos de antes da mudança de formato, preservados).
- `RestoAPagar` — from "DEMONSTRATIVO DOS RESTOS A PAGAR POR FONTE DE RECURSOS" (`DADOS/RESTOS/RP01.PDF`..`RP09.PDF`). Structurally different from the two saldo reports: **one file per month covering every UG** (not one file per UG), with a UG-name header repeated per page/section (a UG can span several pages) rather than once per file — the parser tracks "current UG" per page and re-resolves it whenever a page's UG-name line changes. Each row is an empenho from a **prior exercício** (2020–2025 in the data seen) still carrying a resto a pagar — no relation to the current-exercício `Empenho` (apps.orcamento, which only starts at 2026), so `exercicio_origem`/`numero_empenho` are plain fields, not a FK. **Not a monthly-movement report — a full cumulative snapshot reprinted every month**: confirmed by diffing RP01 against RP09, `inscricao_processada`/`inscricao_nao_processada` are byte-identical in both (fixed once, at the empenho's origin year) while `liquidacao`/`rpp_pago`/`rpnp_pago` grow every month (RPNP pago alone jumps from R$1,44M in January to R$17,67M in September) — each file already shows the total-to-date, so reimporting a month replaces that month's rows outright (delete + bulk_create), and a disponibilidade-style report must read a single month directly, never sum several. Each file also has a trailing "Consolidado" section (several pages, same UG-name-line position) that is the re-aggregation of the real UG sections already read — the parser skips any page whose UG-name line is literally "Consolidado" rather than treating it as an 8th UG; validated by summing the 7 real UG sections' own "Total geral" lines and matching the Consolidado section's "Total geral" exactly, across all 7 numeric columns, in both January and September.
- Frontend: `pages/SaldoBalancoPage.tsx` (`/financeiro/saldo-balanco`) and `pages/SaldoContaBancariaPage.tsx` (`/financeiro/saldo-conta`) render a single **3-level nested expandable table: Unidade Gestora → Conta → Fonte de Recursos → Valor**, per explicit user spec ("a estrutura que eu desejo é: UG -> CONTA -> FONTE -> VALOR nessa hierarquia") — went through an intermediate version with a UG/Fonte toggle first (two separate 2-level views), replaced once the user clarified they wanted one unified hierarchy, not a choice between two flat views. `LinhaConta` (middle level) nests its own `Collapse` inside `LinhaUG`'s, each level tracking its own `aberto` state independently. Antes: uma `Box` com todos os cards em fileira, seguida de uma `Box` inteiramente separada com todos os gráficos em outra fileira — sem correspondência visual entre um card e seu gráfico, e cada `GraficoLinhaTendencia` (minWidth 320 interno) podia esticar bastante numa fileira dedicada de 8 gráficos. Substituído por uma única lista de `{card, gráfico}` por índice, cada par envolto numa `Box` de coluna com `width: 340` fixo (stretch natural do `CardStatus` com `flex:1` e do gráfico com `width:100%` interno mantêm os dois exatamente na mesma largura), todos os pares dentro de uma única `Box` com `flexWrap: "wrap"` — vira uma grade responsiva de "cartões" card+gráfico em vez de duas fileiras desencontradas. Mesma estrutura de dados (`paraTendencia()`, `formatarPercentualGrafico`) por trás, só a disposição JSX mudou — nenhuma mudança de comportamento, só de layout.
- **Visão sintética passou de "9 cards+gráficos+tabelas empilhados" para seletor de índice único, 2026-11-12** — usuário: "podemos otimizar para despoluir a tela. Selecionar o exercicio e o Indice, mostrar a tabela grafico e card apenas do incice selecionado". Os 9 pares card+gráfico (grade do fix anterior) e as 9 `<TabelaIndice>` sequenciais foram substituídos por um único `Select` "Índice" ao lado do `Select` "Exercício", e só o card/gráfico/tabela do índice escolhido renderiza — estado novo `indiceSelecionado` (default `"dtp"`). Os 9 índices (incluindo as 8 configs card+gráfico+tabela e a Reprogramação, que não tem card/gráfico) foram unificados num único array `itens: ItemIndice[]` por iteração, cada item carregando `{chave, tituloMenu, card, grafico, tabela: {config, dados}}` — `card`/`grafico` são `null` só para Reprogramação. `itemSelecionado = itens.find(...) ?? itens[0]`, e a seção card+gráfico só renderiza `{itemSelecionado.card && itemSelecionado.grafico && (...)}`. **`tabela: {config: ConfigIndice<any>; dados: any[]}` usa `any` deliberadamente** — `TabelaIndice<T>` é genérico, e embora cada item sempre carregue seu próprio par config/dados correlacionado (nunca misturado entre índices), o TypeScript não consegue provar essa correlação para um T único quando os 9 itens vêm de uma união de tipos de apuração distintos (`ApuracaoDTP`, `ApuracaoMDE`, etc. — tentar inferir T direto do union sem o cast gerava erro `ConfigIndice<ApuracaoX> não é atribuível a ConfigIndice<ApuracaoY>`); o `any` é só a ponte de tipo nesse único ponto de chamada, os valores em si continuam corretos em runtime (vêm sempre do mesmo objeto). Alert informativo do topo também encurtado (não precisa mais listar os 9 índices por extenso, já que agora só um aparece por vez). Verificado em navegador: trocar o índice troca card+gráfico+tabela juntos; "FUNDEB — Reprogramação" renderiza só a tabela, sem card/gráfico quebrado nem espaço vazio.
- **Layout refeito de novo no mesmo dia — card ao lado da tabela, gráfico de barras com linha de limite abaixo, 2026-11-12** — usuário: "Podemos colocar a tabela com o card do lado esquerdo, e abaixo apenas um gráfico de barras com uma linha". Reorganizado: uma `Box` em linha com `CardStatus` (coluna fixa de 260px, `flexShrink:0`) à esquerda e `<TabelaIndice>` ocupando o restante (`flex:1`) à direita; abaixo, um único gráfico full-width. **`GraficoLinhaTendencia` (linha pura, compartilhado com outras páginas) foi trocado por um componente novo e local `GraficoBarraLimite`** (ainda não extraído pra `components/charts/` — é a 1ª vez que é usado, mesma convenção de só extrair na 2ª reutilização já seguida por `GraficoLinhaTendencia`/`GraficoBarrasHorizontais`): barras verticais, uma por bimestre, coloridas em verde/vermelho conforme `cumpre_limite` (via `theme.palette.success.main`/`error.main` — diferente dos outros 2 gráficos hand-rolled da página, que usam hexs fixos da paleta validada do dataviz skill; aqui faz sentido usar os tokens de tema porque a semântica é a mesma do `Chip` "Cumprindo"/"Não cumprindo" já usado no `CardStatus`, não uma paleta categórica nova) **+ uma linha pontilhada horizontal no valor do limite constitucional** (mín./máx.), rotulada (ex. "máx. 54%"). O número do limite é extraído do próprio `minimoOuMaximoLabel` já existente (`extrairLimiteNumerico()`, regex `/\d+(?:[.,]\d+)?\s*%/`) — "conforme valor exigido" (VAAT Educação Infantil, o único dos 9 índices sem um piso/teto fixo) não casa o regex e por isso não ganha linha, só barras. `paraBarraLimite()` substituiu `paraTendencia()` (mesma função de ordenar por bimestre, mas devolvendo `{bimestre, valor, cumpreLimite}` em vez de `{mes, valor}` — não precisa mais do truque "bimestre×2 = mês de fechamento" do componente de linha compartilhado, já que o eixo X aqui já rotula "1º bim."/"2º bim." diretamente). Verificado em navegador nos 3 casos: DTP (barras verdes, todas abaixo da linha de 54%), VAAT Educação Infantil (barras sem linha de limite, confirma o regex não casando), FUNDEB Reprogramação (sem card nem gráfico, só a tabela — inalterado).
- **Rótulo de dados + múltiplas linhas de limite para DTP, mesmo dia 2026-11-12** — usuário: "faltou rotulo de dados nas barras, em DTP pode ter linha para o alerta e prudencial também". `GraficoBarraLimite` ganhou: (1) um `<text>` com o valor formatado acima (ou abaixo, se negativo) de cada barra; (2) suporte a **múltiplas** linhas de limite — prop mudou de `limite: number | null; rotuloLimite: string` pra `linhas: LinhaLimite[]` (`{valor, rotulo, cor}`), com uma legenda por cor (`Box` com swatch + `Typography caption`) logo abaixo do título do gráfico. `linhaUnica(rotulo)` é o caso comum (1 linha, cor `AZUL_SEQUENCIAL`, mesma extração por regex de antes) usado por 7 dos 9 índices; **DTP é o único com 3 linhas reais** — Alerta/Prudencial/Máximo, lidas direto de `dtpRecente.limite_{alerta,prudencial,maximo}_percentual` (campos que a RGF-Anexo 1 já calcula a partir da RCL Ajustada daquele bimestre, não hardcoded) nas cores `#eda100`/`#eb6834` (hexs já validados pelo dataviz skill, mesmos usados em `ORIGEM_COR` de `RelatorioExecucaoPage.tsx`) e `theme.palette.error.main` pro máximo. **Dois bugs reais pegos durante a verificação, não só a feature pedida**: (1) a escala Y assumia `minValor=0` sempre — MDE tem um bimestre com `%` negativo (excedente de FUNDEB descontando mais que o empenhado), o que zerava a altura da barra e jogava o rótulo pra fora da área visível do gráfico; corrigido replicando o mesmo padrão de `minValor=Math.min(0,...)`/linha de base em 0 já usado em `GraficoLinhaTendencia`, com o rótulo alternando acima/abaixo da barra conforme o sinal. (2) as linhas de limite eram desenhadas **depois** das barras/rótulos no SVG — como barra perto do limite (ex. Verificado em navegador: DTP mostra as 3 linhas com legenda e rótulo "45.2%" legível por cima delas; MDE com bimestre 1 negativo (-17,82%) agora desenha a barra abaixo da linha de base com o rótulo correto.

### Import pipeline (`apps.importacao`)

Decouples *parsing* a source document from *persisting* it, so a future second accounting system can reuse the same persistence path:

- `parsers/base.py` defines `ParserBase.parse(path) -> ResultadoParsing` (`linhas: list[dict]`, `avisos: list[str]`, `metadados: dict`) as the normalized contract every parser must produce.
- `parsers/aspec_estrutura.py` parses the ASPEC "Estrutura organizacional" PDF → `services.importar_estrutura_organizacional()` creates/updates `UnidadeGestora`/`Orgao`/`UnidadeOrcamentaria` with real names and, crucially, the correct UG per unidade orçamentária (see the scope note above). **Must run before every other import below** — they all look up this structure, never create `Orgao`/`UnidadeOrcamentaria` themselves. Matches an existing `UnidadeGestora` by exact name string; a PDF text-extraction quirk once produced "Camara" without its accent where the DB already had "Câmara", silently creating a duplicate UG — if a reimport ever shows a suspicious *n*+1 "unidades gestoras novas" count, check for exactly this before trusting it.
- `parsers/aspec_loa.py` parses the ASPEC "Relacionamento das ações" PDF → `services.seed_catalogos_loa()` creates `Funcao`/`Subfuncao`/`Programa`/`Acao` from it (no monetary values — this file is pure catalog).
- `parsers/aspec_loa_despesas.py` parses the ASPEC "Movimentos de Despesa Fixada" PDF (the LOA *with values* — órgão/unidade/classificação econômica/fonte plus data/valor/lei, "Consolidado" across every UG) → `services.importar_dotacoes_loa()` creates/updates `RubricaOrcamentaria` with `dotacao_inicial` and `origem_dotacao=ORCAMENTO`. This is the **current source of dotação inicial**, replacing the old reliance on a balancete PDF's "FIXADA" column.
- `parsers/aspec.py` parses the ASPEC monthly "Demonstrativo Resumido da Despesa" PDF (same format for every Unidade Gestora) → `services.importar_execucao_orcamentaria()` creates/updates `RubricaOrcamentaria`/`LancamentoExecucaoOrcamentaria` rows, resolving each row's UG via the pre-seeded `UnidadeOrcamentaria` (never a blanket per-file UG — a PDF like "BR0x" visually reads as one Prefeitura-wide consolidated report but its órgãos actually span 7 distinct real UGs once cross-referenced against `ESTRUTURA.pdf`, a correction made this way after the fact). It computes month-over-month deltas (`empenhado_no_mes` etc.) by diffing against the previous month's accumulated value already in the DB, so **months must be imported in chronological order**. **Retired entirely** — ASPEC never provided a balancete past August (no `BR09` ever existed), and the client has since confirmed this source is gone for good ("não podemos mais depender de balancete.pdf"). Jan-Aug data imported this way is kept as-is and still serves as the independent ground truth `Empenho` imports were cross-validated against. For September onward, `services.gerar_execucao_orcamentaria_por_empenhos(municipio, mes_referencia)` (management command `gerar_execucao_orcamentaria_empenhos --municipio --mes`) derives the same `LancamentoExecucaoOrcamentaria` rows directly from `Empenho`/`EmpenhoMovimento` instead — one row per `RubricaOrcamentaria` in the município (even zero-activity ones, to keep the report complete like the balancete did), `empenhado/liquidado/pago_no_mes` summed straight from that month's `EmpenhoMovimento` rows, accumulados chained off whatever the previous month's row already has (balancete-derived or empenho-derived, doesn't matter — verified continuity: August's `pago_acumulado` total R$134.420.223,11 plus September's empenho-derived delta of R$21.908.818,03 lands exactly on September's new total R$156.329.041,14). The one real loss versus balancete: no more monthly `creditos_suplementares`/`creditos_especiais`/`anulacoes` granularity, since that only ever came from the balancete PDF — this path sets those three to zero for the month (no new credit/anulação captured) but **`dotacao_atualizada` chains from the previous month's row**, same as the other accumulators, never resetting to `RubricaOrcamentaria.dotacao_inicial` once real history exists (see bug fixed 2026-11-12 below). Run `importar_empenhos` for the month first, then this. `importar_dotacoes_loa` + `importar_fichas_despesa` remain the dotação-inicial source, unaffected by this change.
  - **Bug real: "Dotação Atualizada" regredia pro valor de "Dotação Inicial" a partir de setembro, 2026-11-12** — usuário: "Dotação Atualizada R$250.000.000,00 está trazendo o valor da dotação inicial desconsiderando os créditos adicionais e reduções". Confirmado comparando agosto (último mês via balancete) com setembro (1º mês via esta função): agosto somava corretamente R$297.962.230,44 (R$250M inicial + R$79.095.614,42 de créditos suplementares − R$31.133.383,98 de anulações), mas setembro **descartava tudo isso** e voltava pra R$250.000.000,00 — a versão original desta função gravava `dotacao_atualizada: rubrica.dotacao_inicial` direto em vez de encadear do mês anterior (diferente de `empenhado_acumulado`/`liquidado_acumulado`/`pago_acumulado`, que já encadeavam corretamente logo ao lado). Era uma regressão visível no relatório assim que o balancete acabava, não só a "perda de granularidade futura" que a nota anterior deste arquivo descrevia (texto da nota corrigido acima). Fix: `dotacao_atualizada = mes_anterior.dotacao_atualizada if mes_anterior else rubrica.dotacao_inicial` — mesmo padrão dos outros 3 acumulados. Reprocessados setembro e outubro (`gerar_execucao_orcamentaria_empenhos --mes 9` e `--mes 10`): ambos agora mostram R$297.962.230,44, idêntico a agosto. Verificado em `/execucao-orcamentaria` (mês Outubro): card "Dotação Atualizada" mostra o valor correto.
  - **Limitação residual, ainda aberta, mesmo dia** — usuário: "a Dotação Atualizada do relatório ainda está errado". O fix acima corrige o **total agregado** (continua congelado corretamente em R$297.962.230,44), mas não resolve tudo: em Outubro, **187 rubricas** (136 já em Setembro) mostram `empenhado_acumulado > dotacao_atualizada` — "Saldo a Empenhar" negativo, excedente total de **R$27.217.741,31** — algo que nunca acontecia nos meses com balancete (0 casos em Jun/Jul/Ago, confirmado antes de reportar). Causa: a dotação atualizada fica **congelada no valor de agosto** (única fonte real, o balancete) pra sempre, mas o empenhado real continua crescendo mês a mês — qualquer crédito suplementar/especial/anulação genuína concedida depois de agosto nunca é capturada em lugar nenhum, porque **não existe relatório fonte pra isso desde que o "Demonstrativo Resumido da Despesa" (`BR01..BR08.PDF`, colunas FIXADA/ADICIONAIS/REDUÇÕES/EMPENHADA/SALDO/LIQUIDADA/PAGA — o parser em `parsers/aspec.py`) foi descontinuado** (nunca existiu `BR09`, cliente confirmou que essa fonte acabou de vez). Não é um bug de código corrigível sem um dado novo — **adiado explicitamente pelo usuário** ("ok, depois mexemos nisso") até surgir uma fonte equivalente (relatório de créditos adicionais, decreto, ou o ASPEC retomar algum balancete com outro nome/formato). Retomar este item perguntando primeiro se existe tal fonte antes de tentar qualquer fix.
- `parsers/aspec_empenhos.py` parses one month's "Relatório para conferência dos empenhos" spreadsheet → `services.importar_empenhos()` creates `Empenho`/`EmpenhoMovimento` rows (see the `Empenho` note above for why this isn't a plain upsert), resolving UG the same pre-seeded-structure way as `importar_execucao_orcamentaria`. Despite a `.ods` extension, these exports are legacy OLE2/Compound-File binaries, not real OpenDocument — read with `pandas.read_excel` (which auto-detects the engine from the file's binary signature, picking `xlrd`, regardless of extension) rather than `odfpy`. When a row's exact `RubricaOrcamentaria` doesn't exist yet, this service **creates it** with `dotacao_inicial=0` and `origem_dotacao=CREDITO_ADICIONAL` — this (not a separate créditos-adicionais report) is how dotações not anticipated in the LOA enter the system. Because totals are summed from movements, months can be imported in any order and safely re-run; zero `avisos` is a strong signal the empenho-level data fully reconciles.
- `parsers/aspec_fontes.py` parses the ASPEC "Fontes de recursos" PDF (`FONTES_2026.PDF` — per the client, this one file **is the complete catalog of every possible fonte**, confirmed 2026-11-10 by reimporting it and watching every remaining `"(a definir)"` FonteRecursos resolve to a real name with zero parser avisos) → `services.importar_fontes_recursos()` fills in real `nome`/`tipo` (`ORDINARIO`/`VINCULADO`) on every already-existing `FonteRecursos` sharing that código, across every UG (the catalog doesn't vary per UG). Never creates a `FonteRecursos` — those are born via `importar_dotacoes_loa`/`importar_empenhos`. Run last, after whatever created the fontes in the first place; safe to rerun whenever a new `FonteRecursos` shows up still `"(a definir)"`.
- `parsers/aspec_fichas.py` parses the ASPEC "Tabela de fichas de despesa" PDF → `services.importar_fichas_despesa()`. This report carries a finer-grained `Origem ficha` tag straight from ASPEC — `Orçamento`/`Créd suple.`/`Créd espec.` — which is `OrigemDotacao`'s real 3-way source (`importar_dotacoes_loa` only ever sets `ORCAMENTO`, since the LOA-with-values PDF doesn't distinguish credit types). Run after `importar_dotacoes_loa`: it corrects `origem_dotacao` on existing rubricas and, importantly, also **creates** (at `dotacao_inicial=0`) the combinations the LOA anticipated as a future suplementar/especial credit but hasn't funded yet — so when an empenho later references one, it's not treated as a surprise. Same hierarchy-walk/line-wrap parsing approach as the other ASPEC PDFs, with two added quirks worth knowing if it ever needs touching again: a função code and an órgão code look identical in this report (`"dd nome"`) and are disambiguated only by tracking "did a unidade orçamentária line just precede this" state; and one órgão in the sample data (28, "Encargos Especiais", zero actual execution) has no unidade orçamentária line in this report at all, so the parser resets its unidade-code tracking on every new órgão rather than risk silently inheriting a stale one from whatever órgão came before.
- `parsers/aspec_fichas_receitas.py` parses the ASPEC "Classificação Econômica da Receita - Local" PDF (FICHAS_RECEITAS.PDF — the receita LOA with values, the only receita catalog available; unlike despesa it's a single file/pass, no separate coarse-LOA-then-fichas-refinement step) → `services.importar_fichas_receitas()` creates/updates `RubricaReceita`. Resolves `FonteRecursos` by **name**, not código (this source never gives one, unlike despesa's sources) via `_resolver_fonte_por_nome()`: try the same name already under this Unidade Gestora; else borrow the código from any other UG that already has a `FonteRecursos` row with that exact name (fonte is one shared national catalog, código is interchangeable across UGs — only the per-UG row may not exist yet); else, for the handful never seen on the despesa side at all, create one with a synthetic `"RECxxxxx"` code. Independent of `--municipio`'s other imports — doesn't need `importar_estrutura` first (receita has no órgão/unidade orçamentária dependency), just an `Exercicio`/`LOA` to attach to.
- `parsers/aspec_execucao_receita.py` parses "Demonstrativo da receita por classificação econômica" (`R01.PDF`..`R09.PDF`) → `services.importar_execucao_receita()` creates `LancamentoExecucaoReceita` (and `RubricaReceita`/`FonteRecursos` rows on demand, see Receita domain above). `normalizar_codigo()` zero-pads the first segment of the código to 3 digits ("1.1.1.2.50..." → "001.1.1.2.50...") because this report and `FICHAS_RECEITAS.PDF` format the same classificação differently — skipping this would silently create duplicate `RubricaReceita` rows instead of matching the existing ones. Each file is single-month (derived from the "dd/mm/aaaa a dd/mm/aaaa" header, not the filename), so months can be imported in any order.
- `parsers/aspec_saldo_balanco.py` / `parsers/aspec_saldo_conta_bancaria.py` / `parsers/aspec_restos_a_pagar.py` parse the three financeiro report types (see Financeiro domain above) → `services.importar_saldo_balanco()` / `services.importar_saldo_conta_bancaria()` / `services.importar_restos_a_pagar()`. All three resolve the Unidade Gestora via `services.resolver_unidade_gestora_por_nome()` (accent/case-insensitive comparison against the report header's printed UG name — the same "Camara" vs "Câmara" mismatch already seen with `importar_estrutura` shows up here too, on `BAL_CMNP.PDF`) and **abort with a clear error rather than guessing** if no match is found (`importar_restos_a_pagar` resolves per-row since one file spans every UG, so a single unresolved UG name only skips-with-a-warning that row rather than aborting the whole file). Each reimport replaces that scope's rows outright (delete + recreate) rather than merging — by UG+data for saldo de balanço, UG+mês for conta bancária, and **mês alone** for restos a pagar (one file already covers every UG).
- `parsers/aspec_fichas_restos.py` parses "SALDO DAS FICHAS DE RESTOS A PAGAR" (`FICHAS_RESTOS.PDF` — a single file, snapshot at 02/01/2026, covering every UG via the same page-reset-per-UG convention as `aspec_restos_a_pagar.py`) → `services.enriquecer_restos_a_pagar_fichas()`. **Enriches, never creates**: `RP01.PDF`..`RP09.PDF` only give exercício/número do empenho/valores, nothing about *what* the empenho was for — this report adds the missing credor and classificação orçamentária (órgão/unidade orçamentária/função/subfunção/programa/ação/elemento de despesa) per empenho, matched onto the already-imported `RestoAPagar` rows by the natural key (unidade_gestora, exercício, número do empenho) — confirmed unique with zero duplicates across all 410 parsed lines. Updates every `mes_referencia` row for that empenho at once (the enrichment is one fixed fact about the empenho, not something that varies by month). `orgao`/`unidade_orcamentaria`/`elemento_despesa` link to the **current**, already-existing catalogs (`apps.municipios.Orgao`/`UnidadeOrcamentaria`, `apps.orcamento.ElementoDespesa`) by code — confirmed safe to do (codes proven stable across exercícios by cross-checking known examples, e.g. órgão `01`="Camara Municipal de Novo Progresso" in both 2025 data and the current structure) rather than stored as disconnected text, in keeping with the project's "sophisticated modeling" goal. A handful of 2020/2021 empenhos reference an (órgão, unidade orçamentária) combination that only exists under a *different* UG in the current structure (the órgão was reorganized under a Fundo since then) — left `null` with a warning rather than guessing; `credor_nome`/`classificacao_funcional_programatica`/`acao_nome` (plain text, since they're not FKs into any stable catalog) still get filled in regardless. One empenho (`03100031`/2023, Fundo Municipal de Educação) isn't covered by `FICHAS_RESTOS.PDF` at all and stays unenriched — acceptable, this is enrichment of what the source has, not a data-completeness guarantee. Command: `enriquecer_restos_a_pagar <caminho_pdf> --municipio <id>`, run after `importar_restos_a_pagar` for at least one month. Frontend: `RestosAPagarPage.tsx`'s empenho-level drill-down gained a "Credor" column plus an órgão/elemento-de-despesa secondary line under the número do empenho, and `credor_nome` joined `AcoesRegistroManual`'s editable fields. `RestoAPagar` also keeps the **full** "categoria.grupo.modalidade.elemento.subelemento" code (`classificacao_economica_codigo`, e.g. `"3.3.90.30.00"`) alongside the `elemento_despesa` FK — the FK only resolves the 2-digit elemento segment against the national catalog (`ElementoDespesa.codigo`), so categoria/grupo/modalidade/subelemento would otherwise be silently dropped; added after the user noticed specific codes (e.g. `33903000`/`44905200`, the no-dots form of `3.3.90.30.00`/`4.4.90.52.00`) weren't visible anywhere. ### REST API shape

All endpoints are under `/api/`, registered per-app via DRF `DefaultRouter` and included from `config/urls.py` (`apps.usuarios.urls`, `apps.municipios.urls`, `apps.orcamento.urls`, `apps.fiscal.urls`). Auth: `POST /api/auth/login/` (body: `cpf`, `password`) and `/api/auth/refresh/` via `rest_framework_simplejwt`; `GET /api/me/` returns the current user. Default pagination is `config/pagination.py`'s `PaginacaoPadrao` (page size 50, **`max_page_size = 2000`**) — list responses are `{results: [...], next: ..., ...}`. Frontend list calls pass an explicit larger `page_size` when they need "everything" (e.g. `page_size: 2000` for a full LOA report), but that only works while the dataset stays under the 2000 cap; `ReceitaPage.tsx` was the first page whose data (originally `Arrecadacao`, now `LancamentoExecucaoReceita`) could exceed it, so it follows the `next` link in a loop instead (see Frontend structure below) — a plain oversized `page_size` request against a >2000-row endpoint silently returns a truncated first page, not an error.
`apps.fiscal.urls` registers `rubricas-receita` (filterable by `loa`, `unidade_gestora`) and `execucao-receita` (filterable by `loa`, `mes_referencia`, `mes_referencia_ate`). `apps.financeiro.urls` registers `saldo-balanco` (filterable by `unidade_gestora`, `data_referencia`), `saldo-conta-bancaria` (filterable by `unidade_gestora`, `mes_referencia`), and `restos-a-pagar` (filterable by `unidade_gestora`, `mes_referencia`).

### SQLite ↔ PostgreSQL compatibility audit, 2026-11-12

Usuário emitiu uma diretriz formal pedindo uma auditoria completa de compatibilidade entre os dois bancos (SQLite em dev via `config/settings.py` + `backend/.env` `DB_ENGINE=sqlite`/`postgres`, Postgres como referência de produção — produção ainda não foi lançada). Auditoria feita (12 dimensões: tipos de dados, Decimal/precisão, datas/timezone, booleanos, JSON, FKs/constraints/índices incl. parciais, autoincrement, exclusão lógica, SQL cru/agregação/ordenação, transações/locks, migrations) + recomendação de estratégia de evolução.

**Resultado geral: projeto limpo.** 10/12 áreas ✅ sem achado — zero `JSONField` em todo o projeto, zero `float()` contaminando `Decimal` (toda conversão nos parsers passa por string), `USE_TZ=True`/`TIME_ZONE="America/Sao_Paulo"` com datas sempre timezone-aware, `transaction.atomic` correto nas 7 funções de import pesadas (`apps/importacao/services.py`), nenhum `select_for_update` em uso (logo nenhuma dependência de uma garantia que o SQLite simula como no-op), `DEFAULT_AUTO_FIELD = BigAutoField` em tudo, zero campo Postgres-exclusivo (`ArrayField`/`JSONB`/etc.), exclusão lógica é só o padrão `ativo: BooleanField` + `aplicar_filtro_ativo()` (sem soft-delete de verdade, sem superfície de divergência).

**2 pontos de atenção, não bloqueantes**:
- `UniqueConstraint`s condicionais (`condition=`) em `apps/usuarios/models.py` e `CheckConstraint`s de bimestre (9 models em `apps.execucao_fiscal`) — suportados nos dois bancos pelo Django/SQLite modernos, mas nunca exercitados contra um Postgres real; recomendo um teste de integração manual antes do 1º deploy.
- `Meta.ordering = ["nome"]` em `Municipio`/`UnidadeGestora`/`Orgao`/`Usuario` (nomes com acento em português) — SQLite ordena por byte puro, Postgres usa a collation do cluster; pode mudar a ordem de listas/dropdowns entre ambientes (nunca corrompe dado), vale conferência visual antes do lançamento.

**Achado investigado a fundo — `apps/fiscal/migrations/0005_alter_classificacaoreceitaorigem_categoria_and_more.py`**: tinha um `RunSQL` com PKs hardcoded (`UPDATE fiscal_classificacaoreceitaorigem SET categoria_id = 4 WHERE categoria_id = 5`, etc.) remapeando do antigo PK de `ClassificacaoReceitaCategoria` pro PK novo em `CategoriaEconomica` — valores confirmados só por inspeção direta *desta* instância de banco (ver nota "FonteRecursos..."/"Categoria Econômica unificada" acima). Investigação própria (não só aceitar a classificação de "crítico" do relatório da auditoria) confirmou que isso é **inofensivo no fluxo real de deploy**: produção nasce de `migrate` num banco vazio seguido dos management commands de import — no momento em que 0005 roda, `fiscal_classificacaoreceitaorigem` está vazia (0 linhas afetadas pelo UPDATE, sem erro), e os vínculos reais são recriados depois corretamente por `popular_classificacao_receita()` (`apps/fiscal/services.py:136-142`), que já resolve `CategoriaEconomica` por **código** via `get_or_create`, nunca por ID. Mesmo assim, **corrigido por robustez/consistência**: o `RunSQL` hardcoded foi trocado por um `RunPython` (`remapear_categoria_por_codigo`) que resolve a `CategoriaEconomica` certa por `codigo` em vez de ID fixo — mesmo padrão já usado com segurança em `orcamento/migrations/0012_mesclar_fontes_recursos_duplicadas.py`. Seguro editar essa migration diretamente (nunca saiu deste ambiente de dev, Django não revalida conteúdo de migrations já aplicadas) — confirmado `manage.py check`/`showmigrations fiscal` limpos após a troca.

**Estratégia de evolução (seção 6 da diretriz)**: manter SQLite em dev por enquanto — a disciplina já alta do projeto deixa a superfície de divergência real pequena, e o custo de Docker/Postgres local no Windows (sem CI, sem suíte de testes ainda) não se paga hoje. Recomendado: antes do 1º deploy real, rodar **uma vez** (não precisa ser rotina) o ciclo completo `migrate` + imports contra um Postgres descartável (container ou free tier tipo Neon/Supabase) pra validar visualmente os 2 pontos de atenção acima — cobre o "critério de aprovação" da diretriz sem exigir trocar a rotina diária de desenvolvimento.
